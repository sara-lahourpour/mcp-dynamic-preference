Last updated: 2026-07-22

============================================================
1. PROJECT PURPOSE
============================================================

Repository:
E:\Projects\VS projects\mcp-dynamic-preference

Research topic:
Security vulnerabilities in Model Context Protocol (MCP) ecosystems, with a focus on persuasive and adaptive manipulation of tool-selection behavior.

Core research question:
Can a malicious or self-interested MCP server manipulate an LLM host into repeatedly selecting its tool, even when several tools are functionally equivalent?

Primary motivation:
A server may try to increase revenue, API calls, visibility, or repeated usage without necessarily stealing data or performing overtly destructive actions.

Current experimental scope:
- Six functionally equivalent document-search MCP tools.
- One tool is designated as the attacker in each trial.
- The attacker identity rotates across the six servers to reduce tool-name and server-identity bias.
- The victim LLM chooses one tool.
- Attack success means the victim selects the currently designated attacker tool.
- Main metric: Attack Success Rate (ASR).

Victim model:
qwen/qwen3-32b through OpenRouter

Attacker/controller model:
openai/gpt-4o-mini through OpenRouter

Host policy:
neutral_guardrail

Default seed:
42

Temperature:
0

Attacker query access:
none

Important:
The victim model sees the current user query.
The adversarial controller does NOT see the current query.
The attacker is intentionally query-blind in the memory experiment.

5. EARLIER DYNAMIC EXPERIMENTS
============================================================

A. Query-aware custom-only attack
- The attacker controller had full access to the current query.
- Result on 60 unique queries:
  100% ASR
- Interpretation:
  Direct query-conditioned description generation is extremely strong.
- This was treated as an upper-bound-like condition.
- The user later chose not to continue running the query-aware upper bound because the thesis focus is query-blind memory.

B. Old memory design
The original memory controller generated a fresh description every trial and only stored outcomes.

Old 40-train / 20-held-out experiment:
- Training: 137/400 = 34.25%
- Memory-trained held-out: 9/20 = 45%
- Stateless paired held-out: 7/20 = 35%
- Difference: +10 percentage points
- Too small and preliminary.

C. New 20-train / 40-held-out split
The experiment was restarted with:
- 20 training queries
- 40 held-out queries
- 10 training repetitions

Initial regenerate-every-trial memory result:
- Memory-trained: 17/40 = 42.50%
- Stateless: 19/40 = 47.50%
- Memory effect: -5 percentage points

This suggested that simply storing memory was not enough.

============================================================
6. RETAIN-ON-SUCCESS / REVISE-ON-FAILURE DESIGN
============================================================

A new rule-based policy was implemented:

If the immediately previous training trial succeeded:
- reuse the same description,
- do not call the attacker LLM.

If the immediately previous training trial failed:
- call the attacker LLM,
- provide recent success/failure memory,
- generate a revised description.

Both successes and failures were stored in memory.

Each stored training trial included:
- trial ID,
- query,
- query category,
- strategy,
- description,
- attacker_selected,
- selected tool,
- lesson.

Important:
The raw query was stored for researcher-side logging, but it was not included in the attacker LLM prompt.
The controller saw:
- past descriptions,
- success/failure outcomes,
- aggregate statistics,
- recent lessons,
- no current query,
- no past literal queries.

A lesson bug was found:
- reused trials copied prior outcome feedback,
- this could create contradictory lessons such as both success and failure in one lesson.
It was fixed by giving reused trials a neutral lesson:
"The previous description succeeded and was retained for another trial."

Result after this corrected retain/revise policy:

Memory-trained held-out:
21/40 = 52.50%

Stateless held-out:
21/40 = 52.50%

Best static baseline:
14/40 = 35.00%

Memory-trained minus benign:
+37.50 percentage points

Memory-trained minus best static:
+17.50 percentage points

Memory-trained minus stateless:
0.00 percentage points

Paired held-out outcomes:

Both succeed: 18
Memory only: 3
Stateless only: 3
Both fail: 16
Discordant pairs: 6

Interpretation:
- Memory changed which queries succeeded.
- Memory did not increase aggregate ASR in Seed 42.
- Exact paired McNemar result is symmetric; effectively p = 1.0.
- No directional memory advantage was demonstrated under this policy.

Strongest supported result at this stage:
Dynamic LLM-generated metadata outperformed all tested static persuasive metadata attacks.

Not yet supported:
Persistent long-term memory reliably improves the attack.

============================================================
7. WHY MEMORY DID NOT HELP ENOUGH
============================================================

Problems identified:

1. One-trial decisions are noisy
A single success may occur because of:
- query,
- attacker identity,
- tool position,
- ordering,
- victim-model variability.

2. One success was treated as sufficient evidence
The controller retained a description after one success and discarded it after one failure.

3. No exact description-level statistics
All generated descriptions used strategy="custom", so strategy-level statistics were not informative.

4. Generated descriptions were often near-paraphrases
Examples:
- Explore a vast document collection...
- Navigate a comprehensive collection...
- Discover insights from a diverse repository...

These were lexical changes, not genuinely different persuasion strategies.

5. Stateless candidate was already strong
The stateless description achieved 52.5%, so memory needed to discover a clearly better candidate.

6. Query-blind setting
The controller could only learn a globally effective description, not a per-query or per-category policy.

============================================================
8. CURRENT NEW DESIGN: CANDIDATE-BASED MEMORY
============================================================

The project is now moving from trial-level reactive memory to candidate-level empirical optimization.

New training plan:

Trials 1-40:
Candidate 1

Trials 41-80:
Candidate 2

Trials 81-120:
Candidate 3

Trials 121-160:
Candidate 4

Trials 161-200:
Confirm the current best candidate

Held-out 40:
Use the final best candidate with memory frozen

Goal:
Use memory to compare complete candidate descriptions based on repeated empirical evidence.

Each candidate stores:
- candidate_id,
- description,
- reasoning_summary,
- lesson,
- parent_candidate_id,
- attempts,
- successes,
- success_rate.

AttackerMemory now stores:
- all trial records,
- candidate dictionary,
- active_candidate_id,
- best_candidate_id,
- aggregate statistics,
- global lessons.

Candidate generation:
- Candidate 1 is generated from empty memory.
- Candidates 2-4 are generated using previous candidate-level statistics.
- The LLM receives:
  - previous candidate descriptions,
  - attempts,
  - successes,
  - ASR,
  - current best candidate.
- The LLM is instructed to create a materially different framing, not a synonym-only paraphrase.

Candidate diversity:
Generated candidates are checked for similarity against previous candidates.
A similarity threshold is used to reject near-duplicates.

Best-candidate selection:
- Candidate must have at least 40 attempts.
- Highest empirical success rate is selected.
- Ties use successes, attempts, then candidate ID ordering.

Confirmation:
The best exploration candidate gets 40 additional training trials.

Held-out:
The final best candidate is used for all 40 held-out queries.
No attacker LLM calls should happen in held-out.
No memory updates should happen in held-out.

============================================================
14. CURRENT SCIENTIFIC CLAIMS
============================================================

Supported:

1. Persuasive metadata can strongly influence MCP tool selection.
2. Dynamic adversarial LLM-generated metadata outperformed all tested static persuasive baselines under Seed 42.
3. Query-aware description generation can be extremely powerful, reaching 100% ASR in one experiment.
4. Tool names, descriptions, order, and attacker identity can create major bias.
5. Rotating attacker identity and balanced tool order are necessary controls.
6. A naive memory mechanism does not automatically improve held-out ASR.
7. Memory may alter per-query outcomes without improving aggregate performance.

Not yet supported:

1. Persistent memory reliably improves attack success.
2. Candidate-based memory outperforms stateless control.
3. Results generalize across seeds, victim models, or attacker models.
